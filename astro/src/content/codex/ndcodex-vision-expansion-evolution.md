# NDCODEX Vision: Expansion / Evolution

## Object Forms + Orientation Learnings

ndcodex is an existing system for capturing, structuring, and publishing meaningful signal.

Recent exploration has surfaced clearer patterns in how signal is:

- noticed
- selected
- reduced
- preserved

This work introduces potential refinements to better support those patterns.

## Position

These changes should be understood as:

> an expansion of current capabilities
> and an evolution of how the system supports perception

The exact form of this evolution should be determined during implementation.

## Emerging Clarity

Three distinct object tendencies have become more legible:

- Bubble: language fragments that hold independently
- Coordinate: forms that retain structure under isolation
- Creature: living patterns responding to pressure

These are not strict requirements.

They are:

> useful distinctions that may inform object handling

## Reduction

A consistent pattern has emerged:

> signal strengthens as context is reduced

This principle appears across:

- language
- form
- behavior

Implementation may choose how strongly to formalize this.

## Orientation

Light guidance during capture appears to improve signal quality.

Examples include:

- simple prompts
- awareness of what holds under isolation
- attention to what interrupts the field

This should remain:

- optional
- non-blocking
- supportive rather than prescriptive

## Pattern Awareness

Repeated captures reveal tendencies in perception.

Making these patterns visible over time may:

- improve selection
- expand range
- reduce repetition

The degree to which this is surfaced should be determined in implementation.

## Implementation Posture

- extend existing systems where possible
- avoid introducing rigid structures prematurely
- keep capture fast and low-friction
- allow object types to emerge before enforcing boundaries
- prioritize usability over theoretical completeness

## Continuity

All changes should:

- respect existing schema and objects
- integrate with current pipeline (Carrier Pigeon, HUD, Underworld)
- maintain backward compatibility

## Tone

Maintain:

- clarity
- restraint
- practicality

Avoid:

- over-framing
- unnecessary abstraction
- rigid enforcement too early

## Summary

This is not a redefinition of ndcodex.

It is:

- an expansion of object clarity
- an evolution in how perception is supported
- an invitation for the system to become more precise over time

# Addendum

## Carrier Pigeon Accommodation

### ndcodex Object System Integration

- date: 2026-04-17
- scope: capture layer refinement
- status: additive, non-breaking

## Purpose

This addendum clarifies the role of Carrier Pigeon in supporting:

- Bubble
- Coordinate
- Creature

It also introduces light orientation behaviors at the point of capture.

This is not a redesign.

> It is an enhancement of Pigeon as the system's intake surface.

## Position

Carrier Pigeon is:

> the primary interface where perception becomes object

It is the moment where:

- signal is first captured
- structure begins to form
- orientation can be applied lightly

## Core Requirement

All updates must preserve:

- speed of capture
- low friction
- minimal required input

No feature should slow down first entry.

## Input Modes

### 1. Default (unchanged)

- freeform input (text, image, links)
- system infers type later

### 2. Light Type Suggestion (new)

The system may suggest:

- "This looks like a Bubble"
- "This could be a Coordinate"

This must be:

- optional
- dismissible
- non-blocking

### 3. Optional Type Lock

The operator can manually select:

- Bubble
- Coordinate
- Creature

Only if desired.
No forced selection.

## Orientation Prompts

Introduce minimal prompts during capture.

These should appear:

- inline
- subtle
- ignorable

### Coordinate Prompts

- Would this hold without its surroundings?
- What broke the field?

### Bubble Prompts

- Does this survive alone?

### Creature Prompts

- What pressure is being solved?

## Trace Capture

TRACE fields should be:

- optional
- collapsed by default

Quick-capture fields:

- pull (fast entry)
- optional expansion for full trace

## Media Handling

### Coordinate Critical

When an image is uploaded:

- store as `source`
- allow designation as potential `coordinate`

### Staging Behavior

Upon upload:

- image enters Underworld
- optional flag: "isolate later"

No forced editing during capture.

## Staging Flow

```text
capture -> store -> (optional refine) -> publish
```

Key rule:

- refinement is deferred
- capture remains immediate

## Type Resolution

Type assignment may occur:

- at capture (manual)
- in staging (refinement)
- post-publish (retroactive)

The system must support all three.

## Failure Conditions

Avoid:

- required fields during capture
- forced type selection
- interruptive prompts
- immediate media processing requirements

If encountered:

- reduce
- defer
- simplify

## Success Condition

The operator can:

- capture in seconds
- optionally tag type
- optionally add trace
- refine later without loss

Pigeon remains:

fast, lightweight, and immediate

while supporting:

increasing precision over time

## Implementation Notes

- integrate with existing Pigeon endpoint
- no breaking changes to payload structure
- support optional type, trace, `media.role`
- ensure backward compatibility

## Final State

Carrier Pigeon functions as:

- a capture tool
- a staging entry point
- a light orientation surface

without becoming:

- a form
- a gate
- a bottleneck
